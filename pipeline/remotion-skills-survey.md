## 2. ADOPT — what to take

### `@remotion/effects` (highest-value finding)

Install: `npx remotion add @remotion/effects` (plus `@remotion/light-leaks` for
`lightLeak()`, `@remotion/starburst` for `starburst()`). Applies to `<Video>`
(from `@remotion/media`), `<Solid>`, `<CanvasImage>`, `<HtmlInCanvas>`:

```tsx
import {blur} from '@remotion/effects/blur';
<Video src={...} effects={[blur({radius: 8})]} />
```

Our `video/src/moves/treatment.tsx` (328 lines) currently hand-rolls grain
(SVG `feTurbulence` reseeded per frame), vignette, a fake bloom ("duplicating
the child, blurring and screening it back"), and CSS `filter: blur()` chromatic
edges. `@remotion/effects` ships GPU-backed, tested equivalents **plus**
effects we don't have at all and would otherwise hand-roll badly:

- Direct replacements: `vignette()`, `noise()`/`whiteNoise()`/`speckle()` (for
  our `FilmGrain`), `glow()` (for our fake-bloom trick), `chromaticAberration()`
  (for our chromatic-edge filter), `blur()` / `linearProgressiveBlur()` /
  `radialProgressiveBlur()` / `zoomBlur()`.
- New capability worth stealing for the "treatment" layer specifically:
  `halftone()`, `scanlines()`, `paper()`/`burlap()` (film-stock texture),
  `lightLeak()`, `pixelate()`/`pixelDissolve()`, `fisheye()`/`barrelDistortion()`
  /`wave()` (lens/glitch distortion family — matches our "montage/glitch" move
  family in `pipeline/vocab-parts/04-montage-loop-glitch.md`).
- `createEffect()` gives a documented path for a *custom* effect (2D canvas or
  WebGL2 shader) that composes in the same `effects` array — useful if a
  reference spec calls for something bespoke, without hand-rolling raw
  `<canvas>` code the way `bloomGlow` currently does.

Caveat to carry over: WebGL2 effects need
`Config.setChromiumOpenGlRenderer('angle')` set during render, or they silently
fail/render blank in headless Chrome — same class of gotcha as the "Chrome
needs an environment map for `metalness`" note already in our own `SKILL.md`
for three.js. Treat this as required boilerplate whenever any WebGL2 effect
from this package is used.

Do not migrate all of `treatment.tsx` in one pass — pick this up per-move as a
1:1 swap when touching a shot, so nothing regresses untested.

## 3. Corrections — things we may be doing wrong

1. **`transform:` strings, not `scale`/`translate`/`rotate` properties.**
   `video/src/moves/camera.tsx` uses `transform: \`scale(${s})\`` and
   `transform: \`rotate${axis}(${deg}deg)\`` throughout (5+ call sites); this
   pattern likely repeats across the other move files. Remotion's own guidance
   (`remotion-markup`, `remotion-interactivity`) is explicit: "Prefer `scale`,
   `translate`, `rotate` CSS properties over `transform`." Their stated reason
   is Studio-editability, which doesn't apply to us — **but** the newer
   `interpolate()` also gained an `output: 'perceptual-scale'` option
   specifically for scale animations (perceptually-linear scaling, since a
   linear 1→2 vs 2→3 scale doesn't *look* like an equal step), which our
   `easings.ts`/`t()`/`ts()` primitives don't expose or use anywhere. This is
   worth a look: if our scale-based moves (zoom entrances, camera push-ins)
   feel like they "snap" at the start of a scale range, `perceptual-scale` is
   the documented fix, and it's only reachable via the discrete `scale`
   property, not a `transform` string. Not urgent, but flag it — this is the
   one place their guidance points at a possible actual visual bug rather than
   a style preference.

2. **`<Audio>` from core `remotion`, not `@remotion/media`.** Our only media
   embed (`video/src/compositions/product-os/mix.tsx`) uses the old
   `<Audio>`/`from "remotion"`. Remotion's docs confirm the old tags "remain
   available for direct use" — so this is not broken — but `@remotion/media`'s
   `<Audio>` is now "the recommended" tag and is the only one that gets
   trimming/volume/speed/pitch controls documented in their `audio.md`
   (referenced, not fetched in depth here) and effects-array support. Since we
   don't currently need pitch-shifting or effects on the music bed, this is a
   should-know, not a should-fix.

3. No image (`<Img>`) or embedded-video usage was found at all in
   `video/src` — confirmed via grep, zero hits. So `<CanvasImage>` (the new
   canvas-based image primitive that effects attach to) doesn't correct
   anything today, it's just the thing to reach for **when** we do add a
   still-image asset that needs an `@remotion/effects` treatment (see §2) —
   `<Img>` cannot take an `effects` prop, `<CanvasImage>` can.

Everything else in their markup/interactivity guidance (inline `interpolate()`,
named easings, opacity-never-alone, `<Sequence>`/`layout="none"` semantics) is
guidance our own `PRINCIPLES.md` and `easings.ts` already independently enforce
or exceed — no gap found there.

## 4. APIs we're not using but should know about

- **`@remotion/effects`** — see §2. Import shape: `@remotion/effects/<slug>`
  (e.g. `@remotion/effects/blur`), except `uvTranslate()`/`xyTranslate()`
  (`@remotion/effects/translate`), `lightLeak()` (`@remotion/light-leaks`),
  `starburst()` (`@remotion/starburst`).
- **`createEffect()`** from `remotion` — factory signature:
  `createEffect<Params, State>({type, label, documentationLink, backend: "2d"|"webgl2"|"webgpu", calculateKey(params), setup(target), apply({source, target, width, height, params, state, flipSourceY}), cleanup(state), schema, validateParams(params)})`.
  Use `backend: "2d"` unless shader math is genuinely needed.
- **`interpolate(..., {output: 'perceptual-scale'})`** — perceptually-linear
  scale easing, only meaningful when animating the `scale` CSS property
  directly (not a `transform` string). Candidate for camera push-ins.
- **`Config.setChromiumOpenGlRenderer('angle')`** (`@remotion/cli/config`) —
  required at render time for any WebGL2 effect; otherwise silent failure.
  Same failure shape as our existing three.js environment-map gotcha.
- Render CLI performance flags we set none of today: `--concurrency`,
  `--scale`, `--gl`, `--jpeg-quality`, `--disallow-parallel-encoding` (lowers
  memory at the cost of speed), `--bundle-cache`. Not a current problem
  (renders succeed), just unused levers if a render ever gets slow or
  memory-constrained.
- **Video-frame safe-area rule** (`remotion-create/video-layout.md`, one
  paragraph): at 1080px width, keep key text ≥80px from the sides and ≥100px
  top/bottom, headline ≥84px, supporting text ≥44px, scaled with composition
  width. Cheap to check our shots against; may already be satisfied by
  `PRINCIPLES.md` but wasn't cross-checked here.

## Verification pass (main agent)

Both ADOPT recommendations were checked against the installed packages before
acting. One held, one did not.

### `perceptual-scale` — ADOPTED, and the survey's target was wrong

Confirmed real in our installed `remotion@4.0.499`
(`dist/cjs/interpolate.js:327`): it interpolates in *signed area* space, because
perceived size follows area and area grows as the square of scale, so a linear
scale ramp reads as decelerating.

The survey suggested checking our camera push-ins. Measured divergence from linear,
as a percentage of the total range:

| move | range | divergence | verdict |
|---|---|---|---|
| `PushIn` | 1 → 1.06 | **0.7%** | imperceptible — left alone |
| `Orbit3D` | 1.09 → 1 | 1.1% | imperceptible — left alone |
| `DollyToUI` | 1 → 2.4 | **10.3%** | changed |
| `ConcentricShapeBurst` | 0 → 9.45 | **24.7%** | changed |

So push-ins were never the problem; the large-range moves were. Added `atScale()`
to `easings.ts` and applied it to those two only. Rendering `ConcentricShapeBurst`
confirms it: the nested copies are now evenly spaced where linear interpolation
bunched them. Rule of thumb recorded in the helper: reach for it above ~1.5x.

### `@remotion/effects` — DOWNGRADED to REFERENCE

The package is real at `4.0.499`, but its own description is "Effects that can be
applied to Remotion-based **canvas** components". Our entire treatment stack is
DOM-based — SVG `feTurbulence` grain, CSS `filter: blur()`, `mixBlendMode`,
`background-clip: text` — and it composites over arbitrary DOM subtrees, including
live UI mockups and text.

So this is not a drop-in replacement for `treatment.tsx`; adopting it would mean
migrating our rendering model from DOM to canvas. That is a rewrite, not an
adoption, and our treatment stack is already built and verified rendering.

Where it IS worth reaching for: effect families we genuinely lack — halftone,
scanlines, light leaks, lens distortion — **on canvas or image content specifically**,
where they would otherwise need a hand-written shader. Reference it then, per shot,
rather than replacing what works.

### Rejected

- `@remotion/media` `<Audio>` — flagged **experimental (WebCodecs-based)** by its own
  package description. Our stable `Audio` from `"remotion"` stays; migrating a
  working, mastered audio pipeline to an experimental package on a recommendation is
  not a trade worth making. Revisit if we need pitch shifting.
- Discrete `scale`/`rotate` CSS properties over `transform` strings — the stated
  reason is Studio editability, which does not apply to us. `atScale()` gives us the
  only substantive benefit without touching 38 call sites.
- Version upgrade — all `@remotion/*` already uniform at `4.0.499`.
